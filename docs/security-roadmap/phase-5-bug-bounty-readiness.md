# Bug bounty readiness (Phase 5)

Bug bounty is **not** where you learn hacking. It is where you report issues **after** you have lab discipline and can read a scope policy.

## Prerequisites (all required)

- [ ] Phase 3: completed beginner path on an **official** lab platform
- [ ] Phase 3: 5+ write-ups with remediation sections
- [ ] Phase 5: target role chosen; bounty is **supplement**, not primary job strategy
- [ ] Can explain difference between in-scope and out-of-scope in one paragraph

## Before your first report

1. Read the program policy end-to-end (scope, exclusions, safe harbor)
2. Use only accounts and assets you created or that the policy explicitly allows
3. Stop at proof of concept — do not exfiltrate extra data to “show impact”
4. Write the report like a lab write-up: class, impact, steps, suggested fix

## Good first program types

| Type | Why |
| ---- | --- |
| Vendor VDP with clear scope | Published rules, often forgiving to newcomers |
| Platform “good for beginners” lists | Curated by community; still read policy yourself |
| Your own staging app | Not bounty, but same report format practice |

## Red lines

- No testing on apps without a published policy
- No social engineering staff unless explicitly in scope
- No DDoS, no physical access, no third-party integrations out of scope
- No sharing findings publicly before fix / coordinated disclosure window

## Readiness self-test

Answer without looking at notes:

1. What is safe harbor?
2. Where do you find out-of-scope assets?
3. What do you do if you accidentally access another user’s data?

If any answer is shaky, stay on authorized labs another month.
